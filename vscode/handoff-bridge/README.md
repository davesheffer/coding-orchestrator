# Coding Orchestrator Handoff Bridge

This local VS Code extension handles `vscode://coding-orchestrator.handoff-bridge/open?id=...` URLs created by the shared rollover helper. It opens a fresh Claude or Codex agent tab using the installed client's commands. Claude receives a prefilled `relay:<id>` prompt. For Codex, it waits until a new tab appears, then copies the full handoff and continuation prompt to the clipboard; paste it and press Enter.

The tab opens in the VS Code window that runs the session writing the handoff. A session started by a VS Code agent extension runs under that window's extension host, so the helper records its ancestor process IDs in the request. The bridge in every window starts with VS Code and checks for pending requests twice a second. Only the bridge whose extension host is one of those ancestors opens the tab. The window that receives the URL ignores a request meant for another window. A helper run outside an extension host, such as in a terminal, sends no ancestors, and the window that receives the URL opens the tab, which is the last active window. Each bridge also deletes requests older than ten minutes.

The URL carries only a random request ID. The request and acknowledgement live under `~/.coding-orchestrator/` (or `ORCHESTRATOR_HANDOFF_HOME`), and requests expire after five minutes. The helper reports a launch only after the extension writes an acknowledgement. It cannot prove that a model has processed the prompt.

For Codex, the bridge copies only a file under `handoffs/`. Symlinks and junctions are resolved, and after opening the file it checks again that the handle is the file the path still resolves to inside `handoffs/`. That catches a replaced file, and a `handoffs/` folder swapped for a link if the swap is still in place after the open; a swap undone between the open and the checks cannot be ruled out, because Node has no way to open a path confined to a folder. A hard link looks like the original file, so the bridge refuses a handoff file with more than one link; the helper always creates a new file. These checks are defense in depth against same-user tampering, not a security boundary.

If no acknowledgement arrives in time, the helper withdraws the request by deleting it; the extension claims a request the same way, so a withdrawn request cannot open a late tab. A request still unclaimed at that point means the extension did not handle the URL in time: VS Code was still starting, or the extension is missing, disabled, or from another version. If the request stays locked by another process (a Windows sharing violation), the helper retries briefly and otherwise warns that a tab may still open late. The helper and this extension must come from the same checkout: reinstall the extension (see the main README) after updating the helper.
